WebRTC (Web Real-Time Communication (ICE / STUN / DTLS / SRTP)): how it works, step by step

WebRTC enables sub-second peer-to-peer browser video, audio, and data channels by discovering public NAT mappings via STUN/TURN, punching holes with ICE, securing keys via DTLS, and streaming encrypted SRTP.

Open the interactive WebRTC animation to watch each packet move and inspect its headers.

WebRTC explained simply

Two friends behind locked apartment gates (NATs) ask a lookout tower (STUN) what their outside gate numbers are, trade those numbers, and then throw video balls directly between gates.

TransportUDP (ICE + DTLS + SRTP / SCTP)
Data formatSDP Offer/Answer + STUN Binding + SRTP Encrypted Media
Common methodsSDP Offer/Answer, STUN Binding, ICE Connectivity Check, DTLS-SRTP

Specifications: RFC 8445: Interactive Connectivity Establishment (ICE).

Devices in the WebRTC exchange

  • Peer A (Behind NAT) (host, 192.168.1.10)
  • STUN / Signaling (server rack, 198.51.100.1)
  • Peer B (Their Laptop) (host, 192.168.0.23)

How WebRTC works, step by step

  1. STUN Public IP Discovery

    Binding Request discovers NAT external IP:port. Peer A queries STUN (UDP 3478) to learn its public reflexive address.

  2. SDP Offer / ICE Candidates

    Exchange codecs & candidate IPs via signaling. Peers swap SDP descriptions and ICE candidate lists through the signaling server.

  3. ICE Hole Punch + DTLS-SRTP

    Direct P2P UDP + encrypted media stream. ICE connectivity checks succeed; DTLS establishes keys for encrypted SRTP audio/video.

What WebRTC looks like on the wire

This is the packet sequence NetPulse replays for a typical WebRTC exchange. Open the animation to inspect each one.

  1. STUN from 192.168.1.10 to 198.51.100.1: STUN Binding Request (Learn public NAT mapping) (72 bytes)
  2. STUN from 198.51.100.1 to 192.168.1.10: Binding Success: XOR-MAPPED 198.51.100.42:51234 (96 bytes)
  3. WebSocket from 192.168.1.10 to 198.51.100.1: Signaling: SDP Offer + ICE Candidates (640 bytes)
  4. WebSocket from 198.51.100.1 to 192.168.0.23: Signaling Relay: SDP Offer -> Peer B (640 bytes)
  5. DTLS from 192.168.1.10 to 192.168.0.23: DTLS Handshake -> Key Export for SRTP (410 bytes)
  6. SRTP from 192.168.1.10 to 192.168.0.23: Encrypted P2P SRTP Audio/Video Stream (Direct!) (1180 bytes)

WebRTC security notes

  • ICE IP Leak. Gathering host/srflx ICE candidates can expose a user’s local LAN or real public IP behind a VPN. Defense: Use mDNS obfuscated host candidates and TURN-only relay policies when IP privacy is required.

Test yourself on WebRTC

What is the purpose of a STUN server in WebRTC?

Answer: To tell a peer its public IP:port behind NAT. STUN returns the XOR-MAPPED-ADDRESS seen from outside the NAT.

When direct P2P hole-punching fails (e.g. symmetric NAT), which server relays WebRTC media?

Answer: TURN. TURN (Traversal Using Relays around NAT) relays media packets as a fallback.

Which protocol encrypts WebRTC audio and video frames?

Answer: SRTP (keyed via DTLS). WebRTC mandates DTLS key exchange paired with SRTP media encryption.
