HTTPS (HTTP over TLS (Secure Hypertext Transfer Protocol)): how it works, step by step

HTTPS wraps HTTP inside TLS encryption, protecting URLs, headers, cookies, and payloads against eavesdropping and tampering while authenticating the server via X.509 certificates.

Open the interactive HTTPS animation to watch each packet move and inspect its headers.

HTTPS explained simply

HTTPS is HTTP inside a locked armored briefcase: the postal worker still sees which building address you’re sending to (IP/SNI), but nobody can read or alter the letter inside.

HTTPS at a glance

OSI layerLayer 7 (Application) over TLS (Layer 6)
Default port443
TransportTCP + TLS 1.2/1.3 (or QUIC for HTTP/3)
Data formatTLS AEAD Encrypted HTTP/1.1 or Binary HTTP/2 Frames
Common methodsGET, POST, PUT, DELETE, HEAD, HSTS

Specifications: RFC 9110: HTTP Semantics (HTTPS URI Scheme); RFC 8446: TLS 1.3.

Devices in the HTTPS exchange

  • Client (host, 192.168.1.10)
  • DNS 8.8.8.8 (dns server, 8.8.8.8)
  • HTTPS Server (web server, 203.0.113.10)

How HTTPS works, step by step

  1. DNS Lookup

    Resolve example.com -> 203.0.113.10. Client resolves the target domain to an IP address via DNS.

  2. TCP Handshake

    Connect to port 443. 3-way TCP handshake establishes the reliable byte stream to port 443.

  3. TLS 1.3 Handshake

    ECDHE + Certificate + ALPN h2. Peers negotiate TLS 1.3 encryption keys and select HTTP/2 via ALPN.

  4. Encrypted HTTP/2 Exchange

    Encrypted GET / -> 200 OK. HTTP headers, cookies, and HTML payload are encrypted end-to-end inside TLS records.

What HTTPS looks like on the wire

This is the packet sequence NetPulse replays for a typical HTTPS exchange. Open the animation to inspect each one.

  1. DNS from 192.168.1.10 to 8.8.8.8: Standard query A secure.example.com (76 bytes)
  2. DNS from 8.8.8.8 to 192.168.1.10: Standard query response A 203.0.113.10 (92 bytes)
  3. TCP from 192.168.1.10 to 203.0.113.10: 54120 -> 443 [SYN] Seq=0 (66 bytes)
  4. TCP from 203.0.113.10 to 192.168.1.10: 443 -> 54120 [SYN, ACK] Seq=0 Ack=1 (66 bytes)
  5. TCP from 192.168.1.10 to 203.0.113.10: 54120 -> 443 [ACK] Seq=1 Ack=1 (60 bytes)
  6. TLS from 192.168.1.10 to 203.0.113.10: ClientHello (TLS 1.3, ALPN=h2, SNI=secure.example.com) (517 bytes)
  7. TLS from 203.0.113.10 to 192.168.1.10: ServerHello + Encrypted Certificate + Finished (1390 bytes)
  8. HTTPS from 192.168.1.10 to 203.0.113.10: Application Data [Encrypted HTTP/2 HEADERS GET /] (210 bytes)
  9. HTTPS from 203.0.113.10 to 192.168.1.10: Application Data [Encrypted HTTP/2 DATA 200 OK] (4200 bytes)

HTTPS security notes

  • SSL Stripping. An on-path attacker intercepts an initial plain HTTP request and prevents the redirect to HTTPS. Defense: Enable HSTS (Strict-Transport-Security) with preload so browsers refuse plain HTTP.

Test yourself on HTTPS

Which default port does HTTPS use?

Answer: 443. HTTPS runs on TCP (or UDP/QUIC) port 443 by default.

In HTTPS, which part of an HTTP request is hidden from network sniffers?

Answer: Path, query string, headers, cookies, and body. Everything inside the HTTP layer (URI path, headers, cookies, body) is encrypted by TLS.

What header prevents SSL-stripping attacks after a user’s first visit?

Answer: Strict-Transport-Security (HSTS). HSTS forces browsers to upgrade all future requests to HTTPS automatically.

Which TLS extension negotiates HTTP/2 vs HTTP/1.1 during the handshake?

Answer: ALPN. Application-Layer Protocol Negotiation (ALPN) picks "h2" or "http/1.1" in 0 extra round-trips.

Why does HTTPS require a Certificate Authority (CA)?

Answer: To sign certificates so browsers trust the server’s public key. CAs vouch that a public key genuinely belongs to the domain name.
