Captive Portal (Wi-Fi Captive Portal (RFC 8910 / HTTP 302 Redirect)): how it works, step by step

Captive portals intercept unauthenticated guest Wi-Fi devices (using DHCP Option 114 or OS connectivity probes like /generate_204) and redirect them via HTTP 302 to a login/terms page before opening the firewall.

Open the interactive Captive Portal animation to watch each packet move and inspect its headers.

Captive Portal explained simply

When you join hotel Wi-Fi, the gateway holds your internet gate shut and points your browser to the check-in desk ("Accept Terms") before letting packets out.

Captive Portal at a glance

OSI layerLayer 7 (HTTP/DHCP Intercept)
Default port80 / 443
TransportUDP (DHCP/DNS) + TCP (HTTP 302)
Data formatDHCP Option 114 / HTTP 302 Redirect + Firewall MAC Allowlist
Common methodsDHCP Option 114, Captive Probe (generate_204), 302 Redirect, Auth Submit, MAC Allowlist

Specifications: RFC 8910: Captive-Portal Identification in DHCP and RAs.

Devices in the Captive Portal exchange

  • Guest Phone (phone, 192.168.10.25)
  • Captive Gateway (access point, 192.168.10.1)
  • Internet Web (web server, 203.0.113.10)

How Captive Portal works, step by step

  1. DHCP + OS Probe

    Phone probes /generate_204 or reads DHCP Option 114. OS detects captive network because probe receives HTTP 302 instead of 204 No Content.

  2. HTTP 302 Redirect to Login

    Gateway redirects to splash login page. Guest sees hotel/airport terms & sign-in portal hosted inside the walled garden.

  3. Firewall Allow & Internet Open

    MAC/IP allowlisted -> 204 probe passes. After sign-in, gateway permits guest MAC through NAT to the open internet.

What Captive Portal looks like on the wire

  1. HTTP from 192.168.10.25 to 192.168.10.1: GET /generate_204 HTTP/1.1 (OS Captive Check) (140 bytes)
  2. HTTP from 192.168.10.1 to 192.168.10.25: HTTP/1.1 302 Found -> Location: http://portal.wifi.local/login (240 bytes)
  3. HTTP from 192.168.10.25 to 192.168.10.1: POST /login (accept_terms=true&voucher=GUEST26) (220 bytes)
  4. HTTP from 192.168.10.1 to 192.168.10.25: 200 OK (MAC Allowlisted in Firewall) (160 bytes)
  5. HTTPS from 192.168.10.25 to 203.0.113.10: Internet Traffic Permitted -> 203.0.113.10:443 (480 bytes)

Captive Portal security notes

  • HTTPS Interception Warnings & MAC Spoofing. Redirecting HTTPS causes cert errors; simple MAC-based allowlists can be bypassed by cloning an authenticated guest’s MAC. Defense: Use DHCP Option 114 (RFC 8910) with HTTP probes and pair with per-user Passpoint/802.1X.

Test yourself on Captive Portal

How do phones automatically pop up a hotel Wi-Fi login sheet?

Answer: They probe a known plain-HTTP URL (e.g. /generate_204) or read DHCP Option 114. OS captive network assistants detect redirects on known probe URLs or RFC 8910 DHCP Option 114.

Why do captive portals redirect plain HTTP rather than HTTPS?

Answer: Intercepting HTTPS triggers a TLS certificate mismatch error in browsers. A gateway cannot forge a valid TLS certificate for google.com, so browsers block MITM redirects on HTTPS.

Which RFC standardizes announcing the captive portal URL directly in DHCP?

Answer: RFC 8910. RFC 8910 defines DHCP Option 114 for Captive-Portal API discovery.
